# 2026-11-01 — building textures

## Goal
The developer asked for real, free textures on buildings (walls, roofs, timber, stone) so they look nicer than flat vertex colour, after a visual-reference search. `SettlementPalette`'s own doc comment already called its colours "placeholders until the retro art pass" (known issues 39, 47, 60).

## What was done
- Found and read [ADR 0015](../decisions/0015-modular-building-kit.md) first: a *proposed* (not accepted) plan to replace `BuildingMesher` with a hand-authored, tagged kit of pieces, explicitly ruling out a texture atlas because walls and roofs need to tile along an arbitrary length. That is a bigger task than "texture the houses the generator already builds" and needs art nobody has drawn. Raised this with the developer before doing any sourcing or wiring; they chose the smaller, scoped pass (texture the existing procedural mesh), which this devlog and [ADR 0030](../decisions/0030-building-texture-pass.md) record.
- Sourced seven CC0 textures from Kenney's "Retro Textures Fantasy" pack (opengameart.org, verified CC0 on the page and in its bundled `License.txt`) at 64 px wide (two are naturally 128 px tall), already in the PS1/retro style the game's own art pillar calls for: `wall_brick_sand_center.png` (plaster), `floor_ground_dirt.png` (mud), `roof_thatch_center.png`, `roof_clay_red_center.png`, `roof_clay_grey_center.png` (cathedral), `floor_wood_planks.png` (beams, doors, roof soffit), `wall_stone.png` (foundation plinth). Picked by eye after extracting and viewing each candidate, not from filenames alone.
- `Realm.Gen.Props.PropMaterial`: a small enum naming what a triangle physically is (`WallPlaster`, `Mud`, `RoofThatch`, `RoofTileRed`, `RoofTileGrey`, `Wood`, `Stone`, or `None`). Added as an optional field on `PropTriangle` (default `None`) and threaded as an optional parameter through the handful of `PropMeshBuilder` methods the textured surfaces actually use (`Triangle`, `Facing`, `FacingQuad`, `FacingPolygon`, `OrientedBox`, `YawBox`, `Prism`). Every other call site in the whole codebase (bridges, city walls, landmarks, roads, crowd) compiles and behaves exactly as before.
- Tagged the specific `BuildingMesher`/`FoundationMesher` calls that build an exterior wall, the roof's top and new soffit, half-timbering beams, a door slab (and its far-mesh painted equivalent), and a stone plinth course.
- `PropMeshConverter.ToTexturedArrayMesh` (new, `ToArrayMesh` untouched): UV comes from a per-triangle dominant-normal-axis planar projection of its own vertex positions, scaled by the material's tile size in metres — no authored UVs anywhere, and it works unchanged for a new generator shape. The texture-array layer (or -1 for `None`) rides in `UV2.x`.
- `BuildingMaterials`: loads the seven PNGs, pads the 64x64 ones to 64x128 by tiling (a `Texture2DArray`'s layers must share one size; the source images are themselves seamless, so stacking a copy underneath loses no seam), builds one `Texture2DArray` and one `ShaderMaterial`. The shader sRGB-decodes the vertex colour itself (replacing `StandardMaterial3D.VertexColorIsSrgb`) and multiplies it onto the sampled texel, or uses it alone when the layer is -1, so every untextured surface in the same mesh (frames, interiors) renders exactly as it did before.
- Wired only the two building-mesh conversions (`CityBuild`'s far mesh, `CityInstance`'s near mesh) to the new converter and material; walls, bridges, landmarks and roads keep `ToArrayMesh`/`CityMaterials.Solid`.

## Decisions made (link ADRs)
[ADR 0030](../decisions/0030-building-texture-pass.md): texture array over atlas (ADR 0015 already ruled out an atlas for the tiling reason, which applies here too); `PropMaterial` as triangle metadata rather than reconstructing material from `Colour` (colour-matching would be fragile — exact float equality across module boundaries — and silently wrong if a palette value ever changes); scope cut to the highest-impact surfaces (walls, roofs, timber, stone, doors), leaving frames/handles/interiors/other city meshes flat for now.

## Problems encountered and how they were solved
- First instinct for `PropMaterial` was to classify a triangle after the fact, by matching its `Colour` against a table of every colour `SettlementPalette` can produce. Dropped before writing it: `BuildingMesher` and `FoundationMesher` already know exactly what they are building at the point they build it, so tagging it there is one optional parameter per call site, not a shade-by-shade reverse lookup that breaks silently if a palette constant changes.
- `Texture2DArray.CreateFromImages` requires every layer to share width, height and format; the pack's wall/door/stone textures are naturally 64x128 while the rest are 64x64. Verified the exact Godot 4.5 `Image`/`Texture2DArray` C# API (`Load`, `Convert`, `CreateEmpty`, `BlitRect`, `CreateFromImages`) before writing `BuildingMaterials.Pad` rather than guessing method names.
- Couldn't visually confirm the result myself: this session has no native-desktop screenshot tool (only Chrome's computer-use tools were loaded), so verification is the Gen-side tests (263 before this devlog's scope, 267 after the geometry fix, material-tagging tests added here) plus a clean game log (no shader-compile or texture-load errors). Said so plainly rather than claiming a visual check that didn't happen; asked the developer to look.

## Tests added
`BuildingMesherTests`: exterior walls tagged `WallPlaster`/`Mud` by style and interior walls untagged, roof top tagged thatch/tile by style and ward and the soffit tagged `Wood`, half-timber beams and the door slab tagged `Wood`. `UnevenGroundTests.AStoneFoundation_IsTaggedTheStoneMaterial`. Full `Realm.Gen.Tests`: 611 before this change (including the roof/foundation fix's own new tests), unaffected; the new material tests bring `Settlements` to 267.
